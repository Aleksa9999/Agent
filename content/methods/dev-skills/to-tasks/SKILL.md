# To Tasks

Разбить спеку на **таски**: вертикальные срезы («трассирующие пули»), каждый из которых объявляет таски, что его **блокируют**.

Ввод пользователя: `$ARGUMENTS` — slug спеки, путь к ней или текстовое описание фичи.

## Процесс

### 1. Найти спеку

По `$ARGUMENTS`: slug → `_specs/<slug>/spec.md`; путь → взять как есть; текстовое описание → сопоставить с каталогами в `_specs/`.

Если аргумента нет — перечислить каталоги `_specs/*/` и спросить пользователя, какой брать.

Прочитать спеку целиком. Секция «Критерии приёмки» — рабочий инструмент этого скилла: разбивка обязана закрыть каждый критерий `К1`…`Кn`, иначе часть фичи потеряется молча. Если секции в спеке нет — сказать об этом пользователю и предложить сначала дописать её через `/to-spec`; нарезать вслепую можно, но покрытие тогда не с чем сверять.

### 2. Проверить, есть ли уже таски

Прочитать `_specs/<slug>/tasks/` целиком, если каталог существует.

**Существующие файлы тасок не трогать и не перенумеровывать никогда** — в них живут статусы, это единственный источник правды о прогрессе. При повторном вызове:

- Разобрать, что уже покрыто существующими тасками, — по строкам «Закрывает критерии» в них, а не на глаз.
- Предложить только новые срезы — под критерии спеки, которые не закрыты ни одной существующей таской.
- Нумерацию продолжить с последнего существующего номера.
- Если новых срезов нет — сказать об этом и остановиться, ничего не записывая.

### 3. Изучить кодовую базу

Если ещё не изучал — разобраться в текущем состоянии кода. Названия и описания тасок должны использовать словарь предметной области проекта.

Искать возможности для префакторинга, который упростит реализацию: «сделай изменение простым, потом сделай простое изменение».

### 4. Набросать вертикальные срезы

<правила-вертикального-среза>

- Срез режет узкий, но ПОЛНЫЙ путь через все слои (схема, API, UI, тесты): вертикально, НЕ горизонтальный срез одного слоя
- Завершённый срез можно продемонстрировать или проверить сам по себе
- Срез рассчитан на одну свежую сессию агента — если не влезает, дробить
- Префакторинг идёт первым

</правила-вертикального-среза>

Каждой таске задать **блокировки**: другие таски, которые обязаны завершиться до её начала. Таска без блокировок может быть взята сразу.

Каждой таске задать и **критерии спеки, которые она закрывает**. Правило простое: к концу разбивки каждый критерий `К1`…`Кn` закрыт хотя бы одной таской. Критерий, не закрытый ничем, — это кусок фичи, который никто не сделает; критерий, размазанный по трём таскам, — повод перепроверить нарезку.

**Широкие рефакторинги — исключение из вертикального среза.** Широкий рефакторинг — это одно механическое изменение (переименовать колонку, сменить тип общего символа), чей радиус поражения расходится по всей кодовой базе: одна правка ломает тысячи мест вызова разом, и ни один вертикальный срез не может остаться зелёным. Не втискивать его в трассирующую пулю; выстроить как **expand–contract**. Сначала expand: добавить новую форму рядом со старой, ничего не ломая. Затем мигрировать места вызова партиями по радиусу поражения (по пакету, по каталогу), каждая партия — своя таска, заблокированная expand'ом; CI остаётся зелёным от партии к партии, потому что старая форма ещё жива. Наконец contract: удалить старую форму, когда не осталось вызывающих, — таска, заблокированная всеми партиями миграции.

### 5. Показать разбивку пользователю

Представить предложенную разбивку нумерованным списком. По каждой таске:

- **Название**: короткое и описательное
- **Блокируется**: какие таски должны завершиться раньше (если есть)
- **Что даёт**: сквозное поведение, которое эта таска заставляет работать
- **Закрывает критерии**: номера из спеки

Следом — карта покрытия одной строкой на критерий: `К1 → 02`, `К2 → 03, 05`. Критерии, не закрытые ничем, вынести отдельно под заголовком «Не закрыто ничем» — это главный вывод шага, а не сноска.

Спросить пользователя:

- Верна ли гранулярность (слишком крупно / слишком мелко)?
- Верны ли блокировки: каждая ли таска зависит только от того, что её действительно гейтит?
- Надо ли какие-то таски объединить или раздробить дальше?
- Если что-то не закрыто ничем — сознательное это решение или пропуск?

Итерировать, пока пользователь не одобрит разбивку.

### 6. Записать таски

Один файл на таску: `_specs/<slug>/tasks/<NN>-<task-slug>.md`, нумерация с `01` в порядке зависимостей (блокирующие раньше). Никогда не сваливать несколько тасок в один файл.

Язык — русский.

Конкретные пути к файлам и фрагменты кода не вставлять — устаревают. Исключение: фрагмент из прототипа, фиксирующий решение точнее прозы (стейт-машина, редьюсер, схема, форма типа) — урезанный до сути решения.

<шаблон-таски>

# NN: <Название таски>

**Статус:** todo

**Блокируется:** номера/названия тасок, которые её гейтят, или «ничем (можно брать сразу)».

**Закрывает критерии:** номера из секции «Критерии приёмки» спеки (`К1`, `К4`), или «нет» для чисто подготовительных тасок вроде префакторинга.

## Что построить

Сквозное поведение, которое эта таска заставляет работать, с точки зрения пользователя, — не послойный список работ.

## Критерии приёмки

Проверяемые условия готовности **этого среза**. Критерии спеки, перечисленные выше, должны оказаться среди них — дословно или уточнёнными до уровня среза; остальное добавляется по нужде.

- [ ] Критерий 1
- [ ] Критерий 2

</шаблон-таски>

**Словарь статусов** — ровно три значения:

| Статус | Значение |
|---|---|
| `todo` | не начата |
| `in-progress` | взята в работу |
| `done` | завершена и проверена |

Состояние «заблокирована» не пишется руками — оно выводится из строки «Блокируется» и статусов тех тасок, на которые она ссылается.

**Спеку не трогать.** Она не содержит статусов и не обновляется по ходу работы: прогресс читается сканом `_specs/<slug>/tasks/`.

### 7. Финальный вывод

```
Таски: _specs/<slug>/tasks/ (<N> шт., новых: <M>)
Покрытие критериев: <закрыто>/<всего><, не закрыто: К..>
Можно брать сразу: NN, NN
Следующий шаг: /implement <slug>
```
