# INSTALL — инструкция для ИИ-агента

Этот файл адресован **агенту** (Claude Code, Codex или другому), которого человек попросил
установить этот пакет. Человеку читать не обязательно — ему адресован `SKILLS-GUIDE.md`.

Выполняй шаги по порядку. Не пропускай шаг 5 (проверка) и шаг 6 (доклад).

---

## Что в пакете

Семь скиллов конвейера разработки: от допроса по идее до ревью готового кода.

```
skills/
├── grill-me/         допрос по продукту раундами
├── to-spec/          разговор → спека с критериями приёмки
├── to-tasks/         спека → вертикальные срезы (таски)
├── implement/        реализация тасок по одной + вызов ревью
├── code-review/      ревью по трём осям (стандарты / спека / безопасность)
├── security-review/  справочник уязвимостей (зовётся осью Безопасность)
└── handoff/          сжать сессию в документ передачи
```

Скиллы связаны между собой: `implement` вызывает `code-review`, `code-review` вызывает
`security-review`. **Ставить их нужно вместе** — если поставить только часть, вызовы
между ними упадут.

---

## Шаг 1. Определи, куда ставить

**По умолчанию установка глобальная** — скиллы должны работать во всех проектах человека,
а не в одном. Отклоняйся от этого только если человек прямо попросил поставить в проект.

Раскладка одинаковая для Claude Code и Codex: каталог на скилл, внутри `SKILL.md`.

| Агент | Глобально (по умолчанию) | В проект |
|---|---|---|
| Claude Code | `~/.claude/skills/` | `<корень проекта>/.claude/skills/` |
| Codex | `~/.codex/skills/` | `<корень проекта>/.codex/skills/` |
| другой агент | найди сам, см. ниже | — |

**Если ты не Claude Code и не Codex:** не угадывай путь. Найди, где твой рантайм ищет
скиллы — в своей документации, в своём конфиге или в переменных окружения. Не нашёл
механизма скиллов вовсе — переходи к шагу 4 («Запасной вариант»).

Ставь в **свой** каталог, а не во все сразу. Если человек пользуется и Claude Code, и
Codex и хочет оба — скопируй в оба, это безопасно: файлы одинаковые.

---

## Шаг 2. Проверь коллизии — до копирования

```bash
ls ~/.claude/skills/    # или ~/.codex/skills/
```

Смотри, нет ли там уже каталога с одним из семи имён.

**Скилл с таким именем уже есть — не перезаписывай молча.** Покажи человеку, какие
именно совпали, и спроси, что делать: заменить, пропустить или поставить под другим
именем. Перезапись чужого скилла без спроса — потеря работы, которую нельзя откатить.

Имени нет — ставь без вопросов, разрешения на установку не переспрашивай.

---

## Шаг 3. Копируй

Из корня распакованного пакета:

```bash
DEST=~/.claude/skills            # или ~/.codex/skills
mkdir -p "$DEST"
cp -R skills/grill-me        "$DEST/"
cp -R skills/to-spec         "$DEST/"
cp -R skills/to-tasks        "$DEST/"
cp -R skills/implement       "$DEST/"
cp -R skills/code-review     "$DEST/"
cp -R skills/security-review "$DEST/"
cp -R skills/handoff         "$DEST/"
```

Правила копирования:

- **Структуру каталогов сохраняй как есть.** У `security-review` внутри лежат
  `references/`, `languages/`, `infrastructure/` — скилл подгружает их по ходу работы.
  Плоское копирование одних `SKILL.md` его сломает.
- **Ничего в скиллах не переписывай.** Ни frontmatter, ни текст, ни пути внутри. Даже
  если тебе кажется, что что-то стоит поправить под этот проект, — это рабочие скиллы,
  а не черновик. Заметил проблему — назови её в докладе на шаге 6, правку не делай.
- **Каталог `.git` не создавай** и никаких файлов от себя в скиллы не добавляй.

---

## Шаг 4. Запасной вариант — если механизма скиллов нет

Некоторые агенты скиллов не поддерживают. Тогда:

1. Положи каталог `skills/` куда-нибудь постоянно, например `~/dev-skills/`.
2. Допиши в файл инструкций агента (`AGENTS.md`, `CLAUDE.md` или его аналог) блок:

```markdown
## Конвейер разработки

В ~/dev-skills/ лежат инструкции конвейера разработки. Когда человек пишет
/grill-me, /to-spec, /to-tasks, /implement, /code-review, /security-review
или /handoff — прочитай ~/dev-skills/<имя>/SKILL.md целиком и работай строго
по нему. Команду толкуй как прямую просьбу выполнить этот процесс.
```

3. Скажи человеку, что у него не нативные скиллы, а эмуляция через файл инструкций:
   работать будет, но менее надёжно — агент может не подхватить инструкцию.

## Шаг 5. Проверь установку

Обязательный шаг. Копирование прошло без ошибки — это ещё не значит, что скиллы видны.

```bash
DEST=~/.claude/skills            # или ~/.codex/skills
for s in grill-me to-spec to-tasks implement code-review security-review handoff; do
  test -f "$DEST/$s/SKILL.md" && echo "ok   $s" || echo "НЕТ  $s"
done
test -d "$DEST/security-review/references" && echo "ok   references" || echo "НЕТ  references"
```

Затем убедись, что рантайм их подхватил: перечитай список доступных скиллов (в Claude
Code это `/skills`; после установки может потребоваться перезапуск сессии). Если семь
новых имён в списке не появились — не докладывай об успехе, разберись или скажи честно,
что скиллы скопированы, но рантайм их пока не видит.

---

## Шаг 6. Доложи человеку

Коротко, по делу:

1. Что поставлено и куда — абсолютным путём.
2. Нужен ли перезапуск сессии, чтобы скиллы стали видны.
3. **Одну строку про то, что это конвейер, а не семь отдельных инструментов**, и что
   подробности — в `SKILLS-GUIDE.md` из этого пакета: «скажи „расскажи, как работают
   скиллы из этого пакета", и я объясню процесс».
4. **Чего не хватает в проекте, чтобы скиллы работали в полную силу.** Если ставишь
   в проекте (а не в пустой системе) — сверься со списком ниже и назови отсутствующие
   файлы: их дешевле завести сейчас, чем переписывать спеку потом. Предложи помочь
   с `CLAUDE.md` — он читается почти всеми скиллами и отдача от него самая большая.
5. Всё, что пошло не по плану: коллизии, пропущенные скиллы, отсутствие механизма скиллов.

Пересказывать `SKILLS-GUIDE.md` в докладе не надо — человек попросит, когда захочет.
Исключение — пункт 4: структуру проекта до него довести нужно сразу.

## Что скиллы ожидают от проекта

Ничего из этого устанавливать не требуется, но знать полезно — и об этом стоит сказать
человеку, если условия не выполнены.

**Обязательное:**

- **Git-репозиторий.** `implement` коммитит, `code-review` считает дифф от фиксированной
  точки. Без git конвейер работает только до `to-tasks`.

**Создаётся само:**

- **Каталог `_specs/`** в корне проекта — его заводит `to-spec` при первом запуске.
  Спеки лежат в `_specs/<slug>/spec.md`, таски — в `_specs/<slug>/tasks/`.

**Необязательное, но усиливает скиллы (если этих файлов нет — скиллы просто работают без них):**

| Файл | Кто читает | Зачем |
|---|---|---|
| `CLAUDE.md` / `AGENTS.md` | `grill-me`, `implement`, `code-review` | правила проекта; для `code-review` это эталон оси Стандарты, а для `grill-me` — карта, какой документ отвечает на какой вопрос |
| `_docs/project.md` | `to-spec` | бизнес-контекст, чтобы спека не противоречила принятым решениям |
| `_docs/stack.md` | `to-spec`, `code-review` | что уже есть в стеке |
| `_docs/design-system.md` | `to-spec`, `implement`, `code-review` | вид фичи описывается существующими токенами, а не выдуманными |

Что писать в каждый файл и что именно теряется, если его нет, — раздел «Структура
проекта» в `SKILLS-GUIDE.md`. Оттуда же бери формулировки, когда докладываешь человеку
по пункту 4 шага 6.

**Что заточено под конкретный стек и не является универсальным** — скажи об этом человеку,
если его проект не такой:

- В `code-review` гейт оси Безопасность перечисляет пути презентационного слоя в виде,
  принятом в Next.js (`app/**/_components/**`, `components/**`). Скилл сам оговаривает:
  в другом проекте читать их как «вёрстка, стили, документация, тесты». Ось при сомнениях
  запускается, так что ошибка этого правила безопасная — лишний прогон, а не пропуск.
- В `implement` полный прогон тестов назван как `npm run test`. В проекте не на npm
  подставляй его настоящую команду.
